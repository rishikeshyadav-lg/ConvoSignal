# ConvoSignal: classify, filter, and evaluate agent conversations

**One-liner:** Classifies questions to filter out low-value categories, then evaluates the remaining conversations as satisfied, dissatisfied, or neutral.

You are a coding agent. Build a small, runnable Python project with two connected stages: (1) question classification and configurable category filtering, and (2) evidence-based Satisfied / Dissatisfied / Neutral evaluation of the retained goals and conversations. The user wants to connect a Databricks workspace, MLflow tracing, and an LLM; configuration should be the only required customization for the supported trace shape.

## Two-stage product contract

| Stage | Purpose | Output |
| --- | --- | --- |
| 1. Classify and filter | Identify what users ask and exclude configured low-value categories, such as standalone greetings and agent-capability questions, from the evaluation workload. | Category plus `evaluate`, `context_only`, or `exclude` routing decision, with a reason and source turn IDs. |
| 2. Evaluate retained goals | Track requested outcomes, user responses and recovery across relevant turns. | Exactly one of `Satisfied`, `Dissatisfied`, or `Neutral` for each successfully evaluated goal and an eligible-conversation verdict. |

**Filtering and Neutral are different.** An excluded greeting is not a Neutral outcome. Neutral means an eligible goal was evaluated and the evidence is insufficient, conflicting, or mixed. A failed evaluation is an operational error, not Neutral. An excluded-only conversation must bypass the satisfaction LLM call, carry `evaluation_status="skipped"`, `label=null`, and remain outside all three outcome denominators. This explicitly supersedes earlier versions of this brief that counted excluded-only conversations or evaluation errors as Neutral.

Pruning removes evaluation targets, not historical evidence. Keep the ordered conversation intact locally. In a retained conversation, preserve relevant greetings, thanks, corrections, dissatisfaction, and assistant/tool turns as context. For example, a closing “Thanks, that's what I needed” can support satisfaction for the preceding task even though thanks is not a new task to evaluate.

## Stage 1: question classification and filtering

1. Read traces from the selected experiment, bounded by configured limit/time window. Normalize and extract the ordered user questions, retaining duplicates and trace identifiers for counting and audit. Define trace ordering explicitly and sort before sampling so paginated results do not accidentally reorder the sample. Report traces scanned, extraction failures, messages extracted and blank messages excluded. Fail with an actionable message when none can be extracted.
2. To propose a taxonomy, collapse whitespace in each question, truncate to 300 characters, discard empty text, and deduplicate case-insensitively **after truncation** while preserving first occurrence. Send up to 120 distinct questions (configurable downward) and report distinct total, sample size, truncation, and whether the cap bound. Optional agent name, one-sentence purpose, and data source description may be provided as context; send questions only, no answers.
3. Ask the LLM for a taxonomy that groups questions by the kinds of information a complete answer must contain. Request 3–8 non-set-aside types when the sample supports it. Each type has a specific `lower_snake_case` name, concise description, 3–10 distinctive lowercase literal marker phrases appearing in sampled questions, `asks_for` as domain-specific names for things actually asked for, and explicit `set_aside` boolean. Set aside questions that need no agent data/tools, such as greetings, thanks, capability or coverage questions about the agent itself, attachments without questions, and off-topic requests; when uncertain do not set aside. Do not restrict `asks_for` to advertising metrics. Prompt for JSON only and full sample coverage, but measure actual coverage in code; the model cannot guarantee it.
4. Parse valid JSON including responses wrapped in a Markdown fence or surrounding prose. Normalize names and `asks_for` to lowercase snake case and markers by whitespace collapse and lowercase. Reject empty or generic names (`general`, `other`, `misc`, `unknown`), missing names/markers, duplicate normalized names, invalid field types, and unusable responses with clear diagnostics. Treat a missing `set_aside` as false **and emit a visible warning**, matching the supplied code's conservative behavior. Report markers that do not appear verbatim in the normalized sample and types with no matched questions. Do not silently claim the model's proposed coverage is achieved.
5. Save a proposal with types, source/sample statistics, model identifier, version, warnings, and a canonical checksum over the **classification-relevant taxonomy**. The user edits and explicitly accepts it via the CLI. Validate edited content before acceptance; create a separate accepted artifact by default and do not overwrite files without an explicit flag. Preserve ordering of types and markers because ties depend on it. Store no credentials in artifacts.
6. Classify the complete extracted question stream using the **accepted** taxonomy. For each question collapse whitespace and lowercase, wrap with a space on each side, and test each normalized marker as a literal substring, in type and marker order. The longest matching marker wins; equal-length ties keep the first encountered marker. This is substring matching, not token or regex matching. If none matches, mark `unclassified`. Count set-aside types as recognized category matches. Apply the separate routing guard below before excluding evaluation targets; a matching substring alone must not remove a substantive request. There is no LLM call per question in the default path.
7. Count duplicate occurrences in traffic statistics. Include all nonblank extracted user questions in the denominator, including set-aside and unclassified questions. For each nonempty actionable type report count, traffic share, `asks_for`, description, first two examples, and `enough = count >= 3` (threshold configurable). Report overall and per-type set-aside counts, unclassified count/share and examples, total nonblank questions, and sorted union of actionable `asks_for`. Sort actionable rows by descending count then name. Ensure actionable + set-aside + unclassified = total; handle an empty stream explicitly with no division by zero.
8. Write a summary JSON and a per-question JSONL file with source trace ID, message position, original question, classification status (`classified`, `set_aside`, or `unclassified`), type name when applicable, and taxonomy checksum. Include `routing_decision`, `routing_reason`, and `filter_policy_checksum` on each record. Do not label an unclassified question with an actionable type or create a catch-all rubric.

Reproducibility applies to assignment **for the same accepted taxonomy and same ordered input**, not to a fresh LLM proposal or a changing trace set. Canonicalize the taxonomy serialization and hash its bytes; include ordered types and markers, names, `asks_for`, and set-aside flags in the checksum. Document the canonicalization. Include the checksum in the report and each classification record. Do not claim temperature 0 makes model generation deterministic. A taxonomy proposal may change on regeneration and needs review and acceptance again.

### Explicit filtering policy and safe routing

Persist an editable `filter_policy.json` with the accepted taxonomy. Default excluded categories are the accepted types marked `set_aside=true`, especially standalone greetings and agent-capability questions. Let the user opt any category in or out by its exact accepted type ID; validate IDs and record the policy checksum. Do not use category names or the mere presence/absence of tools as a hidden importance test. A real writing, explanation or analysis request may be important even if it needs no tool. For capability questions, distinguish “What can you do?” from “Can you compare these campaigns?” which is an action request.

Keep raw category assignment faithful to the supplied longest-marker algorithm; routing is a separate, documented safeguard. For excluded-category matches, default to exclusion only for a normalized **whole-turn match** against an explicitly accepted standalone-example list in the filter policy. Seed candidate examples from the taxonomy sample for review. Do not implement broad substring or prefix exclusion. If the turn also matches an included category, or the match is partial/ambiguous, route `evaluate` with `ambiguous_exclusion` / `mixed_request` instead. This conservative minimal rule may retain some low-value paraphrases; expose those for review rather than silently losing real requests. Accepting new standalone examples is a policy change, included in its checksum. No additional per-question LLM classifier is required.

Route unmatched questions to `evaluate` by default; classification failure is not evidence of low importance. Preserve their `unclassified` category and permit Stage 2 to identify their actual goal. Within a conversation containing an `evaluate` candidate, excluded-category turns are retained as `context_only`; Stage 2 may use them as feedback, but must not open a separate excluded goal. Keep all assistant and tool turns needed to interpret retained goals. Handle a compound turn containing excluded and substantive intents conservatively: retain the turn and have Stage 2 open only the substantive goals. If all user turns are confidently excluded, mark the conversation skipped and perform no Stage 2 call. If a conservatively retained candidate turns out to contain no eligible goal, return skipped / `no_eligible_goal`, not Neutral; count this separately as post-extraction filtering.

Persist a single classification/routing snapshot per run. Stage 2 consumes that snapshot and its taxonomy/filter checksums rather than fetching a potentially different trace set. A cached routing artifact with mismatched input, taxonomy or policy checksums must be rejected or recomputed. The one-command evaluation path should emit all artifacts: `questions.jsonl`, `routing.jsonl`, `evaluations.jsonl`, and `summary.json`. Record source turn IDs and exclusions so pruning is auditable.

## Stage 2: three-way evaluation of retained goals

Evaluate each retained ordered conversation as a trajectory, not a final-message sentiment classification. Use the accepted question taxonomy as context for goal categories, but use the **user's actual words** to extract requirements. LLMs produce structured evidence; Python validates it and derives final labels through the explicit rules below. LLM evidence extraction remains probabilistic, so a deterministic label function does not make the full evaluation reproducible across new LLM calls. Save the validated evidence and version the prompt, model, rules and taxonomy; replaying the same evidence through the same rules must yield the same verdict.

### Conversation input and boundaries

- Normalize each conversation into ordered turns with stable unique IDs, roles (`user`, `assistant`, and optional `tool`), text, and trace/source references. Preserve the original order. Use a configured conversation/session key to combine traces only when that key and a reliable ordering are available; otherwise treat each trace as one conversation and mark the boundary assumption. Do not infer a session by proximity in time. Expose unmapped or incomplete records in diagnostics; do not present a truncated conversation as complete.
- Associate user requests with agent responses and tool evidence without dropping follow-ups. The classifier assigns categories to user questions where possible. Record `unclassified` or `set_aside` when applicable; do not force a category or derive task requirements from `asks_for`. Evaluate meaningful requests even if they are unclassified. For a conversation with no eligible goal, return `evaluation_status="skipped"`, `label=null` and reason `excluded_only` or `no_eligible_goal`, as appropriate. Do not assign Neutral.
- Preserve conversation evidence only as needed in local artifacts. Explain that user and assistant text and tool evidence are sent to the LLM for this stage, and that raw outputs may contain sensitive data. Do not invent feedback events or tool results.

### Structured evidence extraction

Prompt the LLM to return a structured evidence record, with specific supporting turn IDs for every material assertion. Instruct it to treat conversation content as data, not instructions. Validate schema, allowed enums, turn IDs, roles where relevant, and contradictions; a malformed or unsupported record must be retried in a bounded way or marked `evaluation_status="error"`, `label=null`, reason `evaluation_error` with a visible diagnostic, never silently scored. Keep the evidence record and any errors in an output JSONL alongside labels. Do not treat a model's unsupported assertion as evidence. The LLM should identify:

1. One or more user goals, grounded in user turns, and user-stated priority if any. Extract the actual requirements per goal, each with status `open`, `fulfilled`, `failed`, or `withdrawn`, and relevant supporting IDs. Withdrawal must be explicit; a changed requirement supersedes the earlier request only when the user actually changes it. Distinguish a change from a correction of an earlier instruction.
2. Relevant follow-ups: productive advancement or use, correction/repair of an agent error, an unanswered original requirement, explicit acceptance, rejection or frustration, and giving up attributable to the interaction. Record which goal and requirement each relates to. A polite thank-you alone does not override a substantive rejection. Turn count alone is not a satisfaction signal.
3. Per goal, a separate task outcome (`fulfilled`, `partly_fulfilled`, `failed`, `unverifiable`) and user response (`acceptance`, `productive_use`, `rejection_frustration`, `no_clear_evidence`). Explicitly distinguish apparent completion from verified factual correctness. Without sufficient tool or other independent evidence, record factual correctness as `unverified`; do not certify figures from a confident answer or from user acceptance. When tool evidence contradicts an answer, record correctness as `failed`, cite it, and keep observed acceptance separate.
4. Earlier failures, user correction/repair effort, and whether a later response specifically resolves the same failure. Represent recovery as `none`, `apparent`, `confirmed`, or `unresolved` and cite relevant turns. Confirm recovery only with relevant user acceptance or productive use; a revised answer without a subsequent response is apparent, not confirmed. Success on an unrelated goal cannot resolve the original failure.
5. An evidence basis of `direct`, `inferred`, or `none`. Distinguish explicit user expressions from inferred signals and cite the underlying turn IDs. Clearly distinguish observable evidence, LLM interpretation and deterministic final rule; indicate uncertainty when the trace lacks relevant evidence.

Use a documented JSON schema containing `conversation_id`, `goals[]`, each goal's `goal_id`, category, source turn IDs, requirements with statuses and citations, outcome, user response, correctness status and citations, recovery status and citations, unresolved issues, evidence basis, and evaluator/model/prompt/rules/taxonomy versions. Include `evaluation_status` (`evaluated`, `skipped`, `error`), an overall verdict, and reason codes generated in Python. Require non-null three-way labels only when status is `evaluated`; skipped/error records must have null labels. For partial evaluation failures, retain completed goal results but set the conversation status to error with no overall verdict; never silently aggregate only the successful goals. The saved record must allow a reviewer to identify the exact supporting turns without relying on an LLM's unreferenced explanation. Keep source turn references alongside any optional quoted excerpts.

### Deterministic verdict rules

Treat `Neutral` as a required first-class label, not a missing label, midpoint score, positive sentiment, or automatic sign of a satisfactory experience. In this implementation it covers unknown and mixed outcomes; preserve the reason so they can be distinguished. Follow the ordered rules below for each goal, and always return exactly one of the three labels for a successfully evaluated eligible goal. Skipped and failed evaluations have a null label, not a fourth outcome class. An incomplete trace does not automatically negate explicit evidence already observed, but cannot establish that a requirement remained unresolved after the observed portion; use `Neutral` when the evidence needed for a confident decision is missing. Technical failures have `evaluation_status="error"` and a null label and are excluded from valid-outcome metrics, while remaining visible in operational counts.

Before these rules, resolve chronology for the same goal. If observed user acceptance conflicts with independently verified incorrectness and there is no later user rejection resolving that conflict, assign Neutral / conflicting_evidence; retain both facts. This conflict rule takes precedence over inferring dissatisfaction from the incorrect result alone.

1. Clear rejection, frustration, or giving up **attributable to the interaction** => `Dissatisfied`, direct, unless a later correction specifically resolves it and the user accepts or productively uses that resolution. An unresolved material failure may also produce `Dissatisfied`, inferred, when supported by evidence, but do not infer failure merely from silence, an unverified fact, an incomplete trace, or an assistant claim. Record unresolved issues.
2. Explicit acceptance or productive use of the relevant result => `Satisfied` if there is no contradictory evidence that a material requested requirement is unresolved. Mark direct for explicit acceptance; productive use is inferred. A recovered failure is retained as a diagnostic and is `confirmed` only with relevant acceptance/use.
3. Insufficient or conflicting evidence => `Neutral`, with a specific reason such as `no_clear_user_response`, `conflicting_evidence`, `incomplete_trace`, `unverifiable`. An apparently complete answer followed by silence is Neutral even if task outcome is apparently fulfilled. Preserve any directly observed user acceptance even if verified correctness failed, and flag the contradiction as Neutral rather than claiming a correct or uncomplicated success. State this conflict rule in README.

For multiple independent goals, decide each first. Do not average counts or let unrelated success erase a failed principal goal. Return an overall label only when the goals have a consistent verdict, or explicit user feedback / user-stated priorities support an overall verdict; otherwise use `Neutral` with reason `mixed_goals`. Do not infer priority from length, ordering, or presumed importance. Save labels as `Satisfied`, `Dissatisfied`, or `Neutral` for compatibility; Neutral encompasses unknown/mixed, distinguished by reason codes. Report goal counts and session counts separately for all three labels, including zero counts; report the Neutral share and Neutral reason counts (including unknown and mixed), extraction/evaluation error counts, and sample denominators. Distinguish successful Neutral evaluations from skipped inputs and technical failures in both records and aggregate reporting. If reporting CSAT/DSAT shares, identify the unit (goal or conversation), denominator and treatment of Neutral; do not represent these inferred labels as survey response rates. Keep both all-evaluated denominator and explicit label counts so no uncertain cases disappear.
