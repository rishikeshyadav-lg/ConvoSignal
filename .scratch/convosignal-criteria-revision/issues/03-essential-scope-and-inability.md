# 03: Respect essential scope and honest inability

**What to build:** An evaluator user can distinguish a fulfilled current request,
honest inability, optional missing detail and proven essential failure in the
same revised evaluation workflow, without the evaluator silently changing scope.

**Blocked by:** 02 — Recognize supported completion without feedback.

**Status:** ready-for-human

**Implementation:** Complete; verified and available for review. Independent human validation remains pending.

- [x] Explicit campaign identity, reporting periods and requested key metrics
  remain essential unless the user makes them conditional or optional.
- [x] An unfulfilled essential blocks Satisfied despite partial usefulness;
  minor presentation issues and explicitly optional unavailable details do not
  independently establish failure.
- [x] Cited evidence of honest external inability, without another applicable
  failure or rejection, yields Neutral. An unsupported assistant claim of
  inability is not accepted as proof that necessary data were unavailable.
- [x] A substantiated essential failure, such as using the wrong available
  reporting period, permits inferred Dissatisfied without a complaint. Mere
  uncertainty about completion does not.
- [x] A genuine accepted scope change supersedes obsolete requirements while
  preserving history. Giving up or frustration does not silently waive work.
- [x] Necessary pending user input yields Neutral when no separate established
  failure applies; task outcome and user reaction remain separate.
- [x] Evaluation artifacts expose the relevant evidence, requirement states,
  reasons and bases; paired workflow tests exercise all distinctions above and
  keep package/compatibility checks green.
